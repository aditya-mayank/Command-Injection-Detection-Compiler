# Command Injection Detection Compiler (CIDC) - Design Document

## 1. Project Overview
The Command Injection Detection Compiler (CIDC) is a static analysis tool designed to find command injection vulnerabilities in C and C++ source code. It works by analyzing the Intermediate Representation (IR) generated by the Clang compiler.

Command injection (CWE-78) happens when an application passes unsafe user input directly to a system shell (like `system()`, `popen()`, or `exec()`). CIDC traces how variables move through the program to see if untrusted data ever reaches these dangerous functions.

## 2. Architecture
The project is built around a few main components:

1. **Clang/LLVM Frontend:** We use Clang to compile `.c` or `.cpp` files into `.ll` files (LLVM IR). Operating on IR instead of the raw source code makes it easier to track how variables are used, since LLVM puts everything into Single Static Assignment (SSA) form.
2. **C++ Analysis Engine (`ir_scan_v4.exe`):** This is the core engine. It parses the LLVM IR and performs data-flow analysis to track tainted variables. 
3. **Python Flask Backend (`server.py`):** Acts as a web server that handles requests from the user, invokes the C++ engine via `subprocess`, and parses the stdout into JSON.
4. **React Frontend (`app.js`):** A web interface to upload code, view the results, and see the data flow paths visualized using D3.js.

## 3. Data Flow and Taint Tracking
Taint tracking involves identifying three things:
- **Sources:** Where untrusted data enters the program (e.g., `getenv`, `read`, `recv`).
- **Sinks:** Dangerous functions that shouldn't receive untrusted data (e.g., `system`, `popen`, `execve`).
- **Sanitizers:** Functions that clean or validate the input, making it safe to use.

### How the analysis works
The engine reads configuration files (`sources.yaml`, `sinks.yaml`, `sanitizers.yaml`) to know which functions to monitor. 

It then builds a Control Flow Graph (CFG) and traces the variables backwards and forwards across basic blocks. 
- **Intra-procedural:** If `char *x = getenv("USER");` is found, the register holding that address is marked as tainted. If the data is copied into another buffer (`memcpy`, `strcpy`), the taint spreads to the new buffer.
- **Inter-procedural:** If the tainted buffer is passed as an argument to another custom function, the engine recursively analyzes that function call, mapping the argument to the parameter.

To prevent infinite loops during recursive function analysis, we use a visited-set limit tracking the depth of the call stack.

## 4. Remediation Suggestions
The frontend includes a mechanism to suggest fixes for found vulnerabilities. It checks an internal mapping of common vulnerabilities and provides secure alternatives, such as using `execvp` instead of `system()` or passing the variables through a validation function before they hit the sink.

## 5. Performance and Energy Tracking
To monitor the overhead of running this analysis, we integrated `codecarbon` into the Flask backend. This logs the estimated CPU energy usage (in gCO2eq) used during the AST traversal, letting developers see the cost of the security scans. To keep this overhead low, the API hashes every request (SHA-256) and returns cached results if the exact same code is scanned multiple times.

## 6. Known Limitations
Because the engine works on static LLVM IR, complex pointer arithmetic or deeply nested structures (like a struct containing an array of pointers) can sometimes cause the analyzer to lose track of the tainted data. In these specific cases, it might result in a false negative.
